【最優先修正：やったこと】
============================================================

1. メール・パスワードの入力チェックを新規追加（index.html 冒頭付近）
   ・isValidEmail(email) … メール形式チェック
   ・validateAuthInput(email, pass) … 下記の順でチェックし、エラー文言を返す
     - メールアドレス未入力 → 「メールアドレスを入力してください」
     - メール形式が不正     → 「正しいメールアドレスを入力してください」
     - パスワード未入力     → 「パスワードを入力してください」
     - パスワードが6文字未満 → 「パスワードは6文字以上で入力してください」
   → 新規登録・ログインの両方のフォーム（WelcomeGate・RegisterScreen内）で
     送信ボタンを押した瞬間にこのチェックが必ず実行されるようにしました。
     チェックに引っかかった場合はSupabaseへ通信せず、その場でメッセージ表示します。

2. Supabase新規登録処理（signUp）を修正
   ・以前は登録処理の結果を見ずに「必ず次の画面へ進む」実装になっていました。
   ・修正後は、
     - 登録失敗 → エラーメッセージを表示し、その場に留まる
     - 登録成功＋メール確認が必要 → 「確認メールを送信しました」画面を表示（新規追加）
     - 登録成功＋メール確認が不要（Supabase側の設定次第） → プロフィール設定へ進む
   という3パターンに正しく分岐するようにしました。

3. 「確認メールを送信しました」画面を新規追加（ConfirmEmailScreenという名前の新しい画面）
   ・「確認メールを送信しました。メール内のリンクを開いて登録を完了してください」と表示
   ・「確認メールを再送信する」ボタン（Supabaseのresend機能を使用）
   ・「ログイン画面に戻る」ボタン

4. メール未確認ユーザーのホーム画面ブロックを追加
   ・Supabaseのセッションはあるが、メール確認がまだ（email_confirmed_atが無い）場合は
     どの画面から来ても必ず「確認メールを送信しました」画面が表示され、
     プロフィール設定やホーム画面には進めないようにしました。
   ・Googleログインなど、メール確認が不要な認証方法は対象外です。

5. ログイン処理も同様に修正
   ・Supabaseでの認証に成功した場合のみ次の画面（プロフィール設定 or ホーム）に進みます。
   ・失敗時はエラーメッセージを表示し、その場に留まります。

6. 「体験版で始める」ボタンについて（重要な注意点）
   ・このアプリには元から「体験版として先に進める」「まずは体験してみる」という
     ログイン不要の体験モードが用意されています（既存機能）。
   ・今回の修正では、この体験モード自体は既存機能として残しました。
   ・ただし、実際にメール登録した（Supabaseにアカウントがある）ユーザーが
     メール未確認のまま体験モードへ逃げることはできないようにしています
     （4の未確認ブロックが先に効くため）。
   ・「本当に完全ログイン必須のアプリにしたい／体験モード自体を無くしたい」場合は
     別途ご相談ください。仕様に関わる判断なので、今回は既存機能を壊さない方針で
     体験モードは維持しました。

7. パスワード再設定（パスワードを忘れた方はこちら）を追加
   ・ログインフォームの下に「パスワードを忘れた方はこちら」というリンクを追加
   ・タップすると、メールアドレス入力 → resetPasswordForEmail を呼ぶ画面になります
   ・WelcomeGate（最初のログイン画面）とRegisterScreen（登録フロー中のログイン画面）の
     両方に追加しています（画面統合はしていません＝既存の2画面構成を維持）

8. Googleログインボタンを追加
   ・handleGoogleLogin自体は元から用意されていましたが、実際に使われている画面に
     ボタンが無かったため、今回両方の認証フォームに「Googleでログイン」ボタンを追加しました。
   ・Supabase側でGoogle Providerの設定が未完了の場合は、エラーメッセージが
     表示されるだけで、アプリ自体が落ちることはありません。

9. 運動記録などの保存処理を関数化 → Supabase移行しやすくしました
   ・元からあった loadSt() / saveSt() という関数（ユーザーIDごとに保存する仕組み）は
     そのまま活かしています。
   ・新たに syncStateToSupabase() という関数を追加しました。
     ログイン中（体験版ではない）ユーザーの場合、保存するたびに
     Supabaseの user_progress テーブルへも保存を試みます。
   ・テーブルが無い場合はエラーを無視するだけなので、既存の保存動作
     （localStorage / window.storage）には影響しません。

   ▼ Supabase側で以下のテーブルを作成すると、この機能が有効になります。
     SQL Editorで実行してください：

     create table user_progress (
       user_id uuid primary key references auth.users(id),
       data jsonb,
       updated_at timestamptz default now()
     );

     alter table user_progress enable row level security;

     create policy "Users can manage own data"
     on user_progress
     for all
     using (auth.uid() = user_id)
     with check (auth.uid() = user_id);

10. セキュリティ
    ・Supabaseの鍵は Anon(Public) Key のみを使用しています（元から）。
    ・Service Role Key（秘密鍵）は一切使用していません。今後も絶対にフロントエンドの
      コードに書かないでください。

【Supabase管理画面で確認・設定してほしいこと（初心者向け）】
============================================================

■ A. メール確認を必須にするかどうかの確認
   Supabase管理画面 → Authentication → Providers → Email
   「Confirm email」がONになっていることを確認してください。
   ONになっていれば、新規登録後に確認メールが送られ、今回作った
   「確認メールを送信しました」画面が正しく機能します。

■ B. パスワード再設定のリダイレクト先URL許可
   Supabase管理画面 → Authentication → URL Configuration
   「Redirect URLs」に、実際にアプリを公開するURL（例：Netlifyの発行URLなど）を
   追加してください。ここに追加されていないURLへは、確認メールや
   パスワード再設定メールのリンクがうまく戻ってこられません。

■ C. Googleログインを使う場合（任意）
   Supabase管理画面 → Authentication → Providers → Google
   ここでGoogle Cloud Console側のクライアントID・シークレットを設定してください。
   設定が未完了でも、今回の修正でアプリが壊れることはありません
   （ボタンを押すとエラーメッセージが出るだけです）。

■ D. 運動記録のSupabase保存を使う場合（任意・9番の機能）
   Supabase管理画面 → SQL Editor で、上記9番のSQLを実行してテーブルを作成してください。

【今後の改善案】
============================================================
1. app.js / script.jsx / inline.jsx は現在使われていない古いファイルなので、
   混乱を避けるため、将来的に削除するかREADMEで「未使用」と明記するのがおすすめです。
2. プロフィール設定（名前・頻度など）もSupabaseのテーブルに保存すると、
   機種変更時にも引き継げるようになります。
3. 「体験版」ユーザーが後から本登録した場合に、体験版中のデータを
   そのまま引き継げる仕組み（マージ処理）を用意すると親切です。
4. Google/Appleログインを本格的に使うなら、ログイン後の初回だけ
   プロフィール設定に飛ばす分岐をもう少し丁寧に作ると良いです。
5. Supabase保存（syncStateToSupabase）は毎回の保存で呼ばれるため、
   将来的には保存頻度を間引く（デバウンス）と通信量を減らせます。
